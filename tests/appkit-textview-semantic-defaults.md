# Programmatic text-view semantic defaults

New programmatic NSTextView instances use the existing textBackgroundColor and textColor semantic roles for default document surface and default insertion-point color. This follows Apple's [semantic-color Dark Mode guidance](https://developer.apple.com/documentation/uikit/supporting-dark-mode-in-your-interface) and [Dark Mode HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode); the precise choice to tie initial caret to semantic text foreground is conservative project policy, not an observed native default-value claim. The palette policy is documented separately in appkit-semantic-dark-colors.md.

The change is two initializer assignments only. It does not recolor archived text views, loaded document attributes, explicit user background/caret choices, setters or attributed-string colors. Aqua keeps the existing Linux backend white surface/black text/caret; other backends now use their semantic role values. No app/global appearance is enabled here.

Build appkit-textview-semantic-defaults.m linked with AppKit/CoreGraphics, no arguments/NSApplication/window. The original fixture calls real empty NSTextView.drawRect into a padded bitmap under Aqua/Dark/Aqua scopes, samples document pixels and verifies untouched padding. It samples the public insertionPointColor as a CGColor swatch; this is deliberately not a claim to exercise the screen-only blinking-caret raster path. It requires dark default surface/bright distinct insertion color, equality to public semantic background, and restored Aqua output without rebuilding the view. Explicit document background/caret and an attributed document foreground are then assigned and must survive a dark scope unchanged. The foreground preservation check reads the actual attributed color; it does not claim glyph raster coverage for user text.

No nib rewrite, user-content inversion, exact Apple pixels, full TextEdit dark acceptance or complete style/high-contrast support is claimed. Existing explicit document backgrounds can intentionally stay light; forcing those dark requires app-specific semantics and is outside this initializer correction.
